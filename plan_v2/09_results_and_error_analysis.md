## 4. Error Analysis Protocol

### 4.1 Which queries to inspect

Build the sample **by rule, not by browsing**, so it cannot be accused of cherry-picking.

| Stratum | Definition | Sample size (suggested) |
|---|---|--:|
| S1 | **Both fail:** target not in top-100 for E3, E6, E7 and E8 | 25–30 |
| S2 | **Decomposition helps:** E6 rank much better than E3 (e.g. moves from outside top-10 to inside) | 15 |
| S3 | **Reformulation helps:** E7 much better than E3 | 15 |
| S4 | **Decomposition hurts:** E6 clearly worse than E3 | 10–15 |
| S5 | **Reformulation hurts:** E7 clearly worse than E3 | 10–15 |
| S6 | **Hybrid worse than a single retriever** (E3 below max(E1, E2)) | 10–15 |
| S7 | **Reranker hurts:** E9 worse than E8 | 10–15 |
| S8 | **Easy wins:** target at rank 1 for all experiments (to understand what "easy" looks like) | 10 |

Draw each stratum with a fixed random seed. If a stratum has fewer queries than the target size, take all of them and record that number.

### 4.2 Annotation sheet schema (`analysis/error_sheet.csv`)

| Column | Content |
|---|---|
| qid | query id |
| stratum | S1…S8 |
| query_text | original query |
| target_title | **analysis only** (looked up after all runs are final) |
| ranks_E1…E9 | rank of target in each experiment (or `>1000`) |
| decomposition | cached clues |
| reformulation | cached rewrite |
| top3_E8 / top3_E9 | titles of the top 3 returned pages |
| failure_labels | one or more of the categories below, `;`-separated |
| primary_label | the single main cause |
| notes | free text, one or two sentences |
| annotator | initials |

### 4.3 Failure taxonomy (scope §18) with decision rules

| Label | Assign when |
|---|---|
| **Vocabulary mismatch** | The query's key words are absent from the target page's text, but a human sees the connection |
| **Lexical mismatch (BM25)** | BM25 rank is poor while dense rank is good for the same query |
| **Semantic false positive** | A dense or hybrid method ranks a topically similar page above the target |
| **Missing clue** | The query contains a distinctive clue (a rare object, a specific event) that none of the generated clues or the rewrite carries |
| **Incorrect decomposition** | Clues are weak, redundant, or misleading, and the rank gets worse than the original query |
| **Hallucinated clue** | A clue or rewrite includes a specific fact not in the query |
| **Over-general reformulation** | Rewrite is so broad that many irrelevant pages match |
| **Over-specific reformulation** | Rewrite adds details that wrongly narrow the search |
| **Entity ambiguity** | Several pages truly fit the description (for instance remakes, same-name places, siblings) |

Add two labels the scope does not list but you are likely to need: **Noisy/false-memory query** (the user's description contains a wrong detail) and **Truncation** (the matching evidence lies outside the document text the retriever or reranker saw). Mention these as additions.

### 4.3a Comparison with Lin et al.'s error categories

Lin et al. sampled 50 failures (target outside the top 5 for their best system). Add a **paper-comparable sample S0**: 50 random queries where the target is outside the top 5 for your best system (seeded). Map your labels to theirs so the distributions can be compared qualitatively:

| Lin et al. category (their share) | Your labels that map to it |
|---|---|
| Fails to model the query–document relationship (54%) | semantic false positive; vocabulary mismatch; missing clue; entity ambiguity |
| Document representation insufficient (28%) | truncation; short or atypical page (add as a label if you meet it) |
| Query contains an error (18%) | noisy / false-memory query |

Treat noisy / false-memory and document-representation labels as **core**, not optional extras, because both papers highlight them (false-memory queries showed the largest reformulation gain in the 2026 paper, on only 7 queries).

### 4.4 Annotation quality
- If at least two people are available, both annotate **30 shared items**; compute Cohen's kappa on `primary_label`; discuss disagreements and refine the decision rules; then split the rest.
- If working alone, label twice a week apart on a 20-item subset and report your own consistency.
- Keep labels in a spreadsheet with a frozen header; compute the label distribution per stratum using a script.

### 4.5 What to extract
- Label counts overall and per stratum (bar chart).
- Three to five **worked examples** (query, clues, rewrite, ranks across experiments, one-paragraph explanation) for the report: at least one decomposition win, one reformulation win, one case where both fail, one case where an LLM step hurts.
- Patterns: for instance, which entity types or query features correlate with failure. State these as **observations from your sample**, not as general laws.

## 6. Threats to Validity (write this list into the report)

Include each one that applies, with a sentence of explanation.

1. **Corpus setting:** Tier B or C results are not directly comparable with official full-corpus results.
2. **LLM contamination:** Dev3 queries derive from 2024 data that LLMs may have seen in training.
3. **LLM drift and nondeterminism:** API models change; you mitigate with caching, a recorded model id and temperature 0, but cannot fully eliminate it.
4. **Prompt sensitivity:** one frozen prompt per task; different wording could change results.
5. **Single run, single seed:** retrieval and caches are deterministic; the LLM output is one sample per query.
6. **Dev1 tuning:** small development set, so hyperparameter choices carry noise.
7. **Single relevant document:** known-item qrels mark near-duplicates (remakes, redirects) as non-relevant, which can understate performance.
8. **Domain coverage:** Dev3 contains movies, landmarks and celebrities, not the 53 domains of the 2025 test set.
9. **Annotator subjectivity** in the error labels.
10. **Document truncation** affecting dense and cross-encoder methods. The 2026 paper itself reasons that clues may sit deeper than the first few hundred characters of a Wikipedia page.
11. **Dev3 is easier than the official test set.** The 2026 paper reports BM25 nDCG@10 of 0.337 on Dev3 against 0.122 on the Test split. Do not extrapolate Dev3 scores to the official test.
12. **Development data are movie-only** while Dev3 mixes movies, landmarks and celebrities, so prompts and hyperparameters face a domain shift (the same arrangement as the 2026 paper).
13. **Adaptation, not replication:** facets instead of book fields, zero-shot retrievers instead of fine-tuned experts, RRF instead of weighted score sums, and an API LLM instead of 7–8B open models.

## 8. Risks & Mitigations

| Risk | Mitigation |
|---|---|
| Cherry-picked examples | Rule-based, seeded strata |
| Over-interpreting small differences | CIs, correction, "statistically tied" wording |
| Annotation fatigue | Sample sizes above are upper bounds; reduce evenly across strata, not selectively |
| Narrative written before data | Q1–Q7 template; answers only after evidence |
| Analysis changes system after seeing Dev3 | Any post-hoc fix is a labeled extra experiment, never a replacement |
